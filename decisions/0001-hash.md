# 0001 -- The canonical hash: a two-uint32-lane 64-bit non-crypto mix (zero-GC, no BigInt)

Status: accepted (v0.1.0)

## Context

A sketch is only as accurate as its hash -- every accuracy proof (HyperLogLog's
`1.04/sqrt(m)`, Count-Min's `epsilon/w`, ...) ASSUMES uniform, independent
hashing. The zero-dep law means the package must SHIP its own hash; this is
lite-sketch's load-bearing decision, the analog of "which witness" for lite-o1.
It gates every member's accuracy claim, so it is settled before any member.

The hard constraint is that a GOOD hash for these sketches needs real bit-depth.
HyperLogLog's `rho` (the leftmost-1 position of the hash suffix) must range over
the full `64 - p` bits to estimate large cardinalities -- a plain 32-bit hash
gives only `32 - p` bits (~18 at p=14), which caps accuracy. JS has no 64-bit
integer type, and BigInt ALLOCATES (forbidden on the zero-GC hot path).

## The settled calls (user-accepted 2026-09-23)

1. **Realize a 64-bit-quality hash as TWO uint32 LANES (hi, lo) via `Math.imul`.**
   A murmur3-x86 / xxh32-pair-style finalizer over a numeric key + a uint32 seed,
   producing two well-mixed 32-bit lanes. Everything stays in SMI / typed-int
   space -- no BigInt, no boxing. The lanes are returned via two MODULE-SCOPE
   mutable slots (`HASH_HI` / `HASH_LO`) the caller reads immediately, NOT a
   returned object or array -- so the hot path allocates zero bytes.
   - REJECTED: a single 32-bit hash (caps HLL's `rho` at `32 - p`); a 53-bit
     Float64 mix (weaker avalanche, awkward bit-extraction for `rho`); BigInt
     (allocates). The two-lane design is the standard zero-GC-JS answer and the
     reason the "two lanes" option was chosen over both.

2. **HLL reads BOTH lanes for `rho`; Count-Min will take the LO lane `mod w`.**
   Register index = the top `p` bits of `HASH_HI`; `rho` = the leading-zero count
   of the `(64 - p)`-bit suffix formed by `HASH_HI`'s low `32 - p` bits followed
   by all 32 bits of `HASH_LO`, plus one (`Math.clz32` on each lane in turn).

3. **A pre-hashed fast path.** A caller who already has a good hash passes the two
   lanes directly (`addHashed(hi, lo)`), skipping the mix -- the lite-filter
   `keys:'int'` analog. Members document which entry they take.

4. **Independent sub-hashes by SEEDED SALTING from one base hash**, for Count-Min's
   `d` rows (and a future MinHash's `k`): `h_i = mix(h ^ (i * ODD_CONST))`, not `d`
   independent hash functions -- standard, cheap, accuracy-preserving. The seed is
   per-instance (reproducibility; the RandomSet / AliasTable discipline).

5. **Numeric-key CORE + an optional alloc-free string-bytes hasher.** The numeric
   mix is the zero-GC reference; `hashString` walks a string's char codes into the
   lanes WITHOUT retaining a reference (the zero-GC law forbids stored refs, not
   reading bytes). Object keys are the caller's responsibility (hash to a number).

## Consequences

- The hash is testable in isolation: the avalanche property (a 1-bit input flip
  flips ~half the output bits across both lanes) is a shipped gate, and it is what
  makes every member's accuracy claim reproducible and self-contained.
- The two-lane module-slot mechanism keeps `add` / `addHashed` at 0 B/op.
- Future members append below HyperLogLog and reuse this hash by DESIGN-PARITY --
  the shared helper lives above the first class; new members change only the header
  roster comment + `VERSION`.

## Amendment 2026-10-04 (H2.4): the key encoding carries its sign in the high word's top bit

The numeric key is split into two int32 words and folded through the two seeded
murmur3 bodies as `_m3round(lo); _m3round(hiw ^ (neg << 31))`, where
`lo = Math.abs(key) | 0`, `hiw = (Math.abs(key) / 2^32) | 0`, and `neg = key < 0 ? 1 : 0`.

- **The old bit-0 collision.** The original code folded the sign as `hiw ^ neg`, i.e.
  into **bit 0** of the high word -- a MAGNITUDE bit. So `-k` hashed identically to a
  real positive key whose high word differed only in bit 0: `-(H*2^32 + L)` collided
  with `(H ^ 1)*2^32 + L`. `HyperLogLog` undercounted (two keys, one register pattern),
  `CountMinSketch.estimate` aliased a real cell, and `SpaceSaving` -- exact by value in
  the probe -- packed `-k` and its twin into one home slot. The sign now lives in
  **bit 31** of the high word, which is unused because a safe integer's magnitude high
  word is `< 2^21` (`2^53 / 2^32`), so the sign bit never overlaps a magnitude bit and
  `-k` / `k` separate on both lanes. Positive keys and `-0` are bit-identical to before.
- **S1 (editing the hash sites twice).** The sign fix and the int32 word split (F2, Node
  part) touch the SAME six hot sites (`mix64`, HLL `add`, CMS `add`, CMS `estimate`,
  SS `add`, SS `_hash`), so both land in one pass rather than editing each site twice.
- **The murmur hand-inline is deferred to H2.6.** H2.4 ships only the word split + sign;
  hand-inlining the murmur body into `add` would push `add` past V8's 460-byte inline
  cap and DE-inline it, regressing default-tier non-Smi keys from 0-1 to 24 scavenges/op.
  The hand-inline instead moves inside the F5 `_addAt(buf, i)` body (H2.6), whose
  arguments are an object and a Smi, so it never needs to be inlined and costs nothing.

## Amendment 2026-10-04 (H2.6): the hand-inlined murmur, and where the one hash now lives

The H2.4 deferral above is RESOLVED. The murmur body is now hand-inlined into int32 locals in the
hot bodies V8 never inlines anyway (their arguments are an object and a Smi), so a key word `>= 2^31`
never boxes crossing `_m3round`, while `add` stays a small wrapper that DOES inline into the caller.
`mix64` / `hashString` / `saltRow` keep calling the `_m3round` / `_m3final` helpers verbatim (they are
not on a per-op hot path and stay the single readable reference). So the one hash now exists in these
BIT-IDENTICAL copies, all gated by N9 parity against `git show HEAD:Sketch.js`:

- `mix64` + the `_m3round` / `_m3final` helpers (the canonical reference; also `hashString`, `saltRow`);
- `HyperLogLog._addAt` (the full two-lane mix, both rounds per lane);
- `CountMinSketch._addAt` and `CountMinSketch._estimateAt` (the base lane `(hi ^ lo)`, then the per-row
  fmix inlined; D3 -- `_estimateAt` writes the d-cell minimum into `_buf[1]` rather than returning it,
  so a min `>= 2^31` never boxes on the non-inlined return);
- `SpaceSaving._homeAt` (the HI lane -> the map home) and `SpaceSaving._hash` (the reference copy used
  by `merge` placement and the tests).

The three HAND-INLINED copies (`HyperLogLog._addAt`, `CountMinSketch._addAt`, `CountMinSketch._estimateAt`)
use `M3_ADD = 0xe6546b64 | 0`, `k1` from `a | 0`, `k2` from `hiw ^ (neg << 31)` (the H2.4 sign bit),
and the two-compare safe-range check in place of `Math.abs(key) > MAX_SAFE`. `mix64` / `_m3round` /
`_m3final` and SpaceSaving's `_homeAt` / `_hash` are unchanged -- the literal `0xe6546b64` and their
own guards -- so only those three bodies carry `M3_ADD` and the two-compare range check.
