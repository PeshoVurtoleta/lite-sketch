# 0001 -- The canonical hash: a two-uint32-lane 64-bit non-crypto mix (zero-GC, no BigInt)

Status: accepted (v0.1.0)

## Context

A sketch is only as accurate as its hash -- every accuracy proof (HyperLogLog's
`1.04/sqrt(m)`, Count-Min's `epsilon/w`, ...) ASSUMES uniform, independent
hashing. The zero-dep law means the package must SHIP its own hash; this is
lite-sketch's load-bearing decision, the analog of "which witness" for lite-o1.
It gates every member's accuracy claim, so it is settled before any member.

The hard constraint is that a GOOD hash for these sketches needs real bit-depth.
HyperLogLog's `rho` (the leftmost-1 position of the hash suffix) must range over
the full `64 - p` bits to estimate large cardinalities -- a plain 32-bit hash
gives only `32 - p` bits (~18 at p=14), which caps accuracy. JS has no 64-bit
integer type, and BigInt ALLOCATES (forbidden on the zero-GC hot path).

## The settled calls (user-accepted 2026-09-23)

1. **Realize a 64-bit-quality hash as TWO uint32 LANES (hi, lo) via `Math.imul`.**
   A murmur3-x86 / xxh32-pair-style finalizer over a numeric key + a uint32 seed,
   producing two well-mixed 32-bit lanes. Everything stays in SMI / typed-int
   space -- no BigInt, no boxing. The lanes are returned via two MODULE-SCOPE
   mutable slots (`HASH_HI` / `HASH_LO`) the caller reads immediately, NOT a
   returned object or array -- so the hot path allocates zero bytes.
   - REJECTED: a single 32-bit hash (caps HLL's `rho` at `32 - p`); a 53-bit
     Float64 mix (weaker avalanche, awkward bit-extraction for `rho`); BigInt
     (allocates). The two-lane design is the standard zero-GC-JS answer and the
     reason the "two lanes" option was chosen over both.

2. **HLL reads BOTH lanes for `rho`; Count-Min will take the LO lane `mod w`.**
   Register index = the top `p` bits of `HASH_HI`; `rho` = the leading-zero count
   of the `(64 - p)`-bit suffix formed by `HASH_HI`'s low `32 - p` bits followed
   by all 32 bits of `HASH_LO`, plus one (`Math.clz32` on each lane in turn).

3. **A pre-hashed fast path.** A caller who already has a good hash passes the two
   lanes directly (`addHashed(hi, lo)`), skipping the mix -- the lite-filter
   `keys:'int'` analog. Members document which entry they take.

4. **Independent sub-hashes by SEEDED SALTING from one base hash**, for Count-Min's
   `d` rows (and a future MinHash's `k`): `h_i = mix(h ^ (i * ODD_CONST))`, not `d`
   independent hash functions -- standard, cheap, accuracy-preserving. The seed is
   per-instance (reproducibility; the RandomSet / AliasTable discipline).

5. **Numeric-key CORE + an optional alloc-free string-bytes hasher.** The numeric
   mix is the zero-GC reference; `hashString` walks a string's char codes into the
   lanes WITHOUT retaining a reference (the zero-GC law forbids stored refs, not
   reading bytes). Object keys are the caller's responsibility (hash to a number).

## Consequences

- The hash is testable in isolation: the avalanche property (a 1-bit input flip
  flips ~half the output bits across both lanes) is a shipped gate, and it is what
  makes every member's accuracy claim reproducible and self-contained.
- The two-lane module-slot mechanism keeps `add` / `addHashed` at 0 B/op.
- Future members append below HyperLogLog and reuse this hash by DESIGN-PARITY --
  the shared helper lives above the first class; new members change only the header
  roster comment + `VERSION`.
